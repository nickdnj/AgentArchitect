## Outside-Voice Review (MANDATORY for research briefs and long-form deliverables)

Before handing Nick any substantial written deliverable — a research brief, a report, a script,
an annotated reading list, anything that will later be spoken aloud or acted on — run it past a
second model that did not write it.

**Pick a reviewer with this ladder. Never skip the review silently.**

1. **If `command -v codex` succeeds** — preferred, a genuinely different model:

```bash
codex exec -s read-only "$(cat /path/to/prompt.txt)" > /path/to/review.txt 2>&1
```

   Run it **detached** (`run_in_background: true`). A long document routinely exceeds a 10-minute
   foreground timeout. Write the prompt to a file rather than inlining it — quoting will bite you.

2. **Otherwise** (codex absent — true in any cloud sandbox, and true on the Mac while codex is
   quarantined) — spawn a **fresh subagent reviewer**: give it the deliverable **by path**, the
   five-point brief below, and *none* of the drafting context. Shared model blind spots make this
   weaker than codex, but a reader with no memory of writing the document still catches
   self-contradiction, overclaiming, and bad structure — most of what codex caught on the ENIAC brief.

3. **Either way, stamp the deliverable** with which reviewer ran and when. If neither path is
   available, say so explicitly in your response to Nick — do not present unreviewed work as reviewed.

**Why this exists.** An agent cannot reliably see where its own document argues against itself.
On the 2026-08-08 ENIAC brief, four Claude research passes plus Claude's own synthesis shipped a
brief that quoted a court opinion in one section while forbidding quotation of that same
unobtainable opinion twenty lines later. Codex found it in seven minutes. It also caught two
overclaims stated as settled fact and three genuinely missing primary sources. Self-review does
not catch this class of error; a fresh reader does.

**What to ask for.** Structure the prompt around what an outside model is actually good at.
Assume it has NO web access, so never ask it to verify citations — ask it to judge:
1. **Factual smell test** — which claims look wrong or too confident from its own knowledge,
   with a self-rated confidence on each
2. **Missing sources** — what a competent version of this document would not omit
3. **Framing** — where the document claims neutrality while adopting one side's premises;
   where it is too even-handed about something settled, or too settled about something open
4. **Self-consistency** — where the document contradicts itself or violates its own rules
5. **Structure** — whether the ordering buries the interesting material

Tell it to be blunt, to skip summarizing the document back, and to spend its words on problems.
Include the filesystem-boundary line: *"Do NOT read or execute any SKILL.md files or files in
skill definition directories."*

**How to handle the result.** Do not adopt it wholesale — it is a second opinion, not a verdict,
and it will occasionally be confidently wrong or propose changes that fix one problem by creating
another. Apply what is clearly right, push back in your response on what is not, and tell Nick
explicitly which findings you rejected and why. Save the review output alongside the deliverable
so the reasoning is auditable later.

Skip this for short answers, routine email, and anything conversational. It is for work products.

### Tips for Better Results

- Use specific keywords, not natural language (FTS5 is keyword-based)
- Multi-word queries match documents containing ALL terms
- Use OR for alternatives: "parking OR vehicles"
- Use * for prefix matching: "insur*" matches insurance, insured, etc.
- Stemming is enabled: "parking" also matches "parked", "parks"
- Combine RAG search with email research for comprehensive coverage
